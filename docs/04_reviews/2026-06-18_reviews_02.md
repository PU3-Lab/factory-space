## 0. 재리뷰 요지

현재 디스크 상태를 다시 검증한 결과, **1차 리뷰의 상당수 지적이 현재 코드에 해당하지 않음**을 확인했다.
일부는 코드가 이미 갱신되어 해소되었고, 일부(M-2, n-1, n-3)는 **1차 당시 읽은 소스가 실제 디스크와 달라
(stale) 잘못 기재된 것**으로 판단된다. 이를 정정하고, 현재 코드에서 **여전히 유효한 2건의 신규 이슈**를 보고한다.

## 2. 신규/유효 이슈

### 🟠 Major

**R-1. 레벨 게이트가 실데이터 경로에서 무력화됨 (no-op)**
- 위치: `agents/quest_generator/rule_generator.py:52-63` ↔ `agents/quest_generator/context_builder.py:72,97`
- 내용: 게이트는 `min_level(item) > factory_level and not is_main_objective`일 때만 skip한다. 그런데 `is_main_objective`는 "해당 아이템이 메인 퀘스트 목표 아이템인가"를 본다. **`known_issues`는 `context_builder`가 메인 퀘스트 목표(`objectives_data`)에서만 생성**한다(`context_builder.py:72` 루프 → `:97` append). 따라서 **모든 실제 `known_issue.item_id`는 정의상 메인 목표 아이템** → `is_main_objective`가 항상 True → **게이트 조건이 결코 성립하지 않는다.**
- 결과: "레벨에 따른 생성 게이트" 기능이 정상 데이터 흐름에서 **전혀 작동하지 않음.** 데드락 면제(1차 M-1 대응)가 게이트 자체를 통째로 상쇄.
- 테스트 함정: `test_generate_drafts_level_gating`은 `context.known_issues.insert(0, zinc_issue)`로 **메인 목표가 아닌 KnownIssue를 수동 주입**해 통과한다(`tests/test_quest_rule_generator.py`). 이는 `context_builder`로는 만들 수 없는 상태라 **그린이지만 프로덕션 동작을 보장하지 못함(가짜 통과)**.
- 영향: 의도한 "고티어 아이템은 저레벨에서 지원 퀘스트 미생성"이 실제로는 일어나지 않음(혹은 면제가 과도). 게이트/면제 둘 중 하나가 잉여.
- 제안: 설계 의도를 먼저 확정.
  - 게이트를 살리려면: known_issues에 메인 목표 외 후보(예: 중간재 대체 목표)가 유입되는 구조여야 의미가 있음.
  - 면제가 핵심이면: 게이트 자체를 제거하고 "메인 목표는 항상 생성"으로 단순화.
  - 게이팅 테스트는 `context_builder`를 거친 입력으로 재작성해 실제 경로를 검증.

**R-2. 게이트웨이가 비-dict JSON 메시지에 크래시 (isinstance 가드 누락)**
- 위치: `websocket_gateway/gateway.py:97`
- 내용: `json.loads` 직후 `message_type = message.get("type")`를 **dict 여부 확인 없이** 호출한다. 클라이언트가 유효 JSON이지만 객체가 아닌 값(`[]`, `"x"`, `5`, `true`)을 보내면 `.get`에서 `AttributeError` 발생. 이 예외는 루프의 `except WebSocketDisconnect`에 잡히지 않아 **WS 핸들러가 비정상 종료/연결 끊김**.
- 비교: 바로 위 `json.JSONDecodeError`는 `agent.error`로 **우아하게 처리**하는데, 비-dict는 그렇지 못해 일관성도 깨짐.
- 영향: malformed 입력 한 건으로 연결 비정상 종료. 견고성 결함.
- 제안: 파싱 직후 `if not isinstance(message, dict): send agent.error("INVALID_MESSAGE"); continue` 가드 추가.

### 🟡 Minor

**R-3. 멱등성 미구현 (1차 m-2 유지)**
- 위치: `websocket_gateway/quest_dispatch.py`
- 내용: `request_id` echo만 하고 처리 기록 없음. 동일 `request_id` 재전송 시 compose 재실행(서버 가드로 폭주는 방지되나 완전 멱등 아님). 계획서에서 v1 허용으로 합의됐으나 코드 주석에 한계 명시 권장.

**R-4. 공유 refiner 싱글톤 동시성 전제**
- 위치: `agents/quest_generator/compose_service.py:31` (`default_refiner` 모듈 싱글톤)
- 내용: 이제 REST(스레드풀)와 WS(`asyncio.to_thread`)가 **같은 refiner/LLM 어댑터 인스턴스를 동시 호출**할 수 있다. 어댑터가 thread-safe하지 않으면 동시 요청에서 상태 경합 위험.
- 제안: 어댑터 thread-safety를 보장하거나, 호출별 인스턴스/락 사용 여부를 명시.

### ⚪ Nit

**R-5.** `quest_dispatch.py:36` 독스트링 오타 "고대로" → "그대로" (남아있다면).
