## 3. 신규 발견 사항 (테스트·의존성)

심각도: 🔴 Blocker · 🟠 Major · 🟡 Minor · ⚪ Nit

### 🟠 T1. 마이그레이션이 테스트에서 전혀 검증되지 않음 (B2가 무방비)

- 위치: `backend/tests/agents/material_generation/conftest.py:19-22`, `backend/migrations/versions/0002_create_material_generation_tables.py`
- 내용: conftest는 alembic 마이그레이션을 거치지 않고 `RecipeModel.__table__.create(engine)`처럼 모델의 테이블 객체로 직접 생성한다. 이 경로는 모델의 `func.now()`(→ SQLite `CURRENT_TIMESTAMP`)를 쓰므로 정상 동작하지만, 마이그레이션의 `sa.text('now()')`는 우회된다.
- 영향: 16개 테스트가 모두 통과해도 **B2(마이그레이션 SQLite 실패)는 절대 드러나지 않는다.** 실제 배포 스키마 경로(alembic)에 대한 테스트 커버리지가 0이다.
- 제안: alembic `upgrade head`로 임시 SQLite DB를 만들고 한 건 INSERT 하는 smoke 테스트 추가.

### 🟡 T2. `test_experiment_hash...order_independent`가 순서 독립성을 검증하지 않음

- 위치: `backend/tests/agents/material_generation/test_normalizer.py:31-46`
- 내용: 테스트 이름은 "order independent"인데 `inputs1`과 `inputs2`가 **동일한 순서**라 사실상 동일 입력의 안정성만 검증한다. 게다가 `generate_experiment_hash`는 내부 정렬을 하지 않으므로(정렬은 선행 `normalize_inputs`에 의존) 함수 단독으로는 순서 독립적이지 않다.
- 영향: 실제로 보장되지 않는 속성을 보장하는 듯한 착시. 누군가 `normalize_inputs` 호출을 생략하면 같은 조합이 다른 해시를 낳아 캐시 미스가 발생하는데 테스트가 못 잡는다.
- 제안: `inputs2`를 역순으로 구성하고, 반드시 `normalize_inputs`를 거친 결과로 해시를 비교하도록 수정.

### 🟡 T3. fallback 경로 테스트가 LLM 부재(env)에 암묵 의존

- 위치: `backend/tests/agents/material_generation/test_agent.py:48-63`
- 내용: `test_agent_synthesize_new_material_fallback_path`는 `"Fallback" in res.name`을 기대한다. 이는 테스트 환경에 LLM이 설정되지 않아 `adapter.invoke`가 실패 → `get_fallback_proposal`로 빠지기 때문에 통과한다. 어댑터를 mock하지 않으므로, LLM env가 설정된 개발자 환경에서는 실제 LLM을 호출해 이름에 "Fallback"이 없어 **실패/flaky**가 된다.
- 제안: `adapter.invoke`(또는 `generate_proposal`)를 명시적으로 mock하여 fallback 경로를 결정론적으로 강제.

### 🟡 T4. 테스트 커버리지 공백 — 핵심 버그 경로 미검증

- 위치: `backend/tests/agents/material_generation/`
- 내용: 다음 경로에 대한 테스트가 없다.
  - M2: `test_agent_synthesize_experiment_cached_reuse`는 `material_id`/`name`만 비교하고 `rarity`/`visual_status`를 단언하지 않아 캐시 필드 누락을 잡지 못함.
  - M3: 중복 `item_id` 입력.
  - M1: 동시 요청/IntegrityError.
  - `recipe_match`(레시피 직매칭) 응답, `similarity` 서비스, `result_validator`의 클램핑·금칙어·후보 수 제한, `visual_pipeline` 등.
- 제안: 최소한 `result_validator`와 `recipe_match`/`lookup_cache`(필드 완전성 포함) 단위 테스트 보강.

### ⚪ D1. `db/models.py`가 pgvector에 하드 결합

- 위치: `backend/src/db/models.py:21,27` → `agents/operator_guide/rag_schema.py:5,22,35`
- 내용: 신규 모델 `Base`가 `rag_schema`의 `metadata`(Postgres 전용 `Vector` 컬럼을 가진 RAG 테이블이 등록된 동일 `MetaData`)를 재사용한다. 그 결과 `db.models` 임포트는 `pgvector` 설치를 강제하고(모듈/앱/ingest 전체 전파), 신규 테이블이 pgvector 테이블과 같은 MetaData에 묶인다.
- 영향: 현재 `Base.metadata.create_all()` 사용처는 없어 즉각적 장애는 없으나, SQLite 기본 설정에서 metadata 전체 생성 시도 시 pgvector 테이블 생성으로 실패할 잠재 위험. B2와 함께 "SQLite 기본 설정 미지원" 문제를 가중.
- 제안: 신규 도메인은 별도 `MetaData`/`DeclarativeBase`로 분리하거나, pgvector 의존을 RAG 모듈 내부로 한정.
