## 1. 변경 요약

- `agents/new_material_generator.py`(단순 프롬프트 에이전트)를 제거하고 `agents/material_generation/` 패키지로 대체.
- LangGraph 서브그래프 기반 동기(sync) 합성 파이프라인 도입: `normalize → lookup_cache → recipe_match → prevalidate → classify → handle_rule → similarity_context → llm_propose → validate_result → deduplicate_material → register_material`.
- SQLAlchemy 동기 엔진/모델(`db/engine.py`, `db/models.py`) 및 4개 테이블 마이그레이션 추가(`recipes`, `generated_experiments`, `generated_materials`, `generated_material_discoveries`).
- HTTP 라우터(`/api/v1/experiments/material-creation`, `/api/v1/materials/{id}/visual-status`) 및 WS 파이프라인 노드(`synthesize_material`) 양쪽 진입점 연결.
- 레시피 CSV ingest 스크립트, 비주얼 에셋 파이프라인(시뮬레이션, daemon 스레드) 추가.

전반적으로 캐시 → 레시피 매칭 → 규칙 분류 → LLM 제안 → 검증/재시도 → 중복제거 → 등록의 단계 설계는 명확하고 책임 분리가 잘 되어 있다. 아래는 머지 전 처리해야 할 이슈 목록이다.

## 2. 이슈 목록

심각도: 🔴 Blocker · 🟠 Major · 🟡 Minor · ⚪ Nit

### 🔴 B1. `RecipeRepository` 클래스 캐시가 최초 로드 후 영구 미갱신

- 위치: `backend/src/agents/material_generation/recipe_repository.py:34`, `:49`
- 내용: `_known_items` / `_recipes_cache`는 **클래스 속성(프로세스 전역)**이며 `is None`일 때만 reload한다. 서버가 레시피 ingest 전에 기동되어 첫 요청이 들어오면 캐시가 **빈 set/list**로 고정되고, 이후 재시작 전까지 절대 갱신되지 않는다.
- 영향: `prevalidator`의 `known_items`가 영원히 비어 모든 입력이 `unknown_item`으로 거부됨. 또한 서로 다른 DB 세션을 쓰는 테스트 간 캐시 누수 발생.
- 제안: 빈 결과는 캐싱하지 않거나, ingest 후 명시적 `reload_cache()` 호출 훅을 두고, 가능하면 요청 스코프(또는 TTL) 캐시로 전환.

> **[조치 완료 - 2026-06-12]** 캐시가 비어 있거나 None일 때 reload하도록 `recipe_repository.py`의 캐시 조회 조건을 보완하여 최초 DB가 비어 있던 상황에서 나중에 레시피가 로드되더라도 갱신되도록 해결했습니다.

### 🔴 B2. 마이그레이션이 SQLite에서 실패 — `sa.text('now()')`

- 위치: `backend/migrations/versions/0002_create_material_generation_tables.py:41` 외 전체 `created_at/updated_at` 컬럼
- 내용: 기본 `DATABASE_URL`은 `sqlite:///./factory_space.db`(`db/engine.py:17`)인데, 마이그레이션은 `server_default=sa.text('now()')`를 하드코딩했다. SQLite에는 `now()` 함수가 없어 INSERT 시 `OperationalError: no such function: now`로 실패한다. 모델은 방언별로 컴파일되는 `func.now()`를 쓰는데 마이그레이션만 리터럴 텍스트라 불일치.
- 영향: 기본 설정(SQLite)에서 모든 실험/물질 저장 실패.
- 제안: `func.now()` 사용 또는 Postgres 전용임을 명시. (보너스: `revision` 식별자 `'0002_create_material_tables'`가 파일명/docstring과 불일치 — alembic 동작엔 무해하나 정리 권장.)

> **[조치 완료 - 2026-06-12]** `server_default` 구문을 PostgreSQL/SQLite 공용 표준 문법인 `CURRENT_TIMESTAMP`로 변경해 SQLite 환경에서도 오류 없이 마이그레이션이 완수되도록 수정했습니다.

### 🟠 M1. 동일 실험 동시 요청 시 캐시 반환 대신 IntegrityError

- 위치: `backend/src/agents/material_generation/graph.py:117`, `registry/experiment_registry.py:33`
- 내용: `experiment_hash`에 unique 제약이 있는데, 두 요청이 동시에 같은 조합으로 들어오면 둘 다 `lookup_cache`를 miss하고 둘 다 `save_experiment → flush`에 도달한다. 두 번째는 unique 위반으로 트랜잭션 전체 롤백 후 `SYNTHESIS_ERROR` 반환(캐시 히트로 graceful degrade되지 않음).
- 제안: `IntegrityError` 캐치 후 재조회(get-by-hash) 경로 추가.

> **[조치 완료 - 2026-06-12]** `save_experiment` 및 `save_material` 등록 시 nested transaction(`begin_nested()`)을 이용해 unique hash 제약조건 충돌 예외 발생 시 Graceful하게 `merge` 처리하도록 보강하여 동시성 레이스를 제어했습니다.

### 🟠 M2. 캐시된 `new_material` 응답이 신규 생성 응답과 필드 불일치

- 위치: `backend/src/agents/material_generation/graph.py:69-75` vs `:343`
- 내용: `lookup_cache_node`의 cached `new_material` 경로는 `material_id`, `name`만 채우고 `rarity`, `visual_status`, `fallback_icon`, `material_hash`를 비운다. 신규 경로는 전부 채움.
- 영향: 클라이언트가 캐시 히트 시 해당 필드를 `null`로 받아 응답 계약 불일치.
- 제안: 캐시 경로에서도 `GeneratedMaterialModel` 조회로 전 필드 채우기.

> **[조치 완료 - 2026-06-12]** 캐시 조회 성공 분기(`lookup_cache_node`)에서도 `GeneratedMaterialModel`로부터 `rarity`, `visual_status`, `fallback_icon` 등 전체 속성을 조회해 빈 구멍 없이 완벽하게 바인딩하도록 보강했습니다.

### 🟠 M3. 중복 `item_id` 입력이 해시와 레시피 매칭에서 다르게 처리됨

- 위치: `backend/src/agents/material_generation/normalizer.py:17`, `recipe_repository.py:53`
- 내용: `normalize_inputs`는 중복 `item_id`를 병합하지 않는다. 입력 `[iron:1, iron:1]`이면 `experiment_hash`는 `"iron:1|iron:1"`로 계산되지만, `match_recipe`의 `input_map = {item_id: qty}` 컴프리헨션은 마지막 값만 남겨 `{iron:1}`이 된다. 즉 철 2개를 넣었는데 철 1개 레시피에 매칭됨.
- 제안: normalize 단계에서 동일 `item_id` 수량 합산.

> **[조치 완료 - 2026-06-12]** `normalize_inputs` 단계에서 동일한 `item_id`가 중복 유입될 시 사전에 수량을 합산하여 가공하도록 해시와 매칭 로직의 정합성을 일치시켰습니다.

### 🟡 m1. 비주얼 파이프라인 daemon 스레드 — 종료 시 업데이트 유실 + 무제한 생성

- 위치: `backend/src/agents/material_generation/events.py:26`, `visual_pipeline.py:30`
- 내용: 신물질마다 `daemon=True` 스레드가 `time.sleep(2)` 후 DB를 쓴다. 프로세스 종료 시 daemon 스레드는 강제 종료되어 해당 물질이 `pending`에 영구히 갇히고, 부하 시 스레드가 무제한 생성된다.
- 제안: `BackgroundTasks` 또는 작업 큐로 추적 가능하게 전환.

### 🟡 m2. `find_similar_experiments`가 전체 테이블 로드 후 파이썬 필터

- 위치: `backend/src/agents/material_generation/similarity.py:28-39`
- 내용: `machine_type` + `result_type="new_material"`인 **모든** 실험을 쿼리해 파이썬에서 overlap 계산/정렬. 테이블 증가 시 매 요청마다 전체 스캔.
- 제안: 입력 item_id로 DB 측 필터(JSON 쿼리 또는 정규화된 인덱스 테이블).

### 🟡 m3. `recipe_name`을 `failure_reason` 컬럼에 오버로딩

- 제안: `recipe_name` 전용 컬럼 또는 `output_items_json` 메타로 분리.

### 🟡 m4. `get_material_by_hash` 중복 호출

## 4. 긍정적인 부분

- LangGraph 노드별 단일 책임 분리와 조건부 라우팅이 명확.
- 결정론적 사전검증(prevalidate/classify)으로 불필요한 LLM 호출을 줄이는 흐름이 합리적.
- `result_validator`의 속성 클램핑·금칙어·후보 수 제한 등 LLM 출력 sanitization이 견고.
- 실험/물질 이중 해시(experiment_hash, material_hash)로 캐시와 중복제거를 분리한 설계가 적절.
