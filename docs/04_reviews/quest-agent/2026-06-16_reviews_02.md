## 변경 요약

Quest Agent를 기획서 v3 기반으로 독립 구현하기 위한 MVP 작업 계획. 핵심 결정은 두 가지다.

1. **게임 상태(인벤토리·레벨·메인퀘스트·해금)는 클라이언트가 payload로 전달** → 서버는 게임 상태에 대해 stateless, 퀘스트 인스턴스/진행도만 영속화.
2. **기획서 22장 최소 버전 우선**, 단 1차 지원 타입은 기획 검토 결과 `produce_item` → `collect_item`으로 교체.

계획서 `0.1`절에 기획 검토 8건을 보정 결정으로 정리하고 Phase 1~7에 분배했다. 본 리뷰는 그 보정안에 남은 내부 모순과 설계 구멍을 점검한 것이다.

## 이슈 목록

### 🔴 Blocker

**[B-1] `collect_item` 완료 판정이 flow(이벤트 누적) 기반이라 이슈 1 수정이 무효화됨**
- 위치: `2026-06-16-quest-agent-mvp-plan.md:153-156` (Phase 6) vs `:30` (0.1-#1)
- 내용: 보유량(재고) 정렬을 위해 타입을 `collect_item`으로 바꿨으나, Phase 6은 `item_collected` 이벤트의 `amount`를 `current_amount += amount`로 누적한다. 이는 다시 흐름(flow) 측정이다.
- 영향: 10개 수집 후 5개 소비 시 누적값 10(완료)이지만 실제 보유 5 → "보유량 달성"이 거짓 완료된다. 이슈 1에서 지적한 흐름/재고 괴리가 collect_item에 재발하여, 보정 결정의 목적 자체가 깨진다.
- 제안: `item_collected` 이벤트가 현재 보유 총량 스냅샷(`current_total`)을 싣고, 트래커는 `current_amount = current_total`(대입), 완료는 `current_total >= target_amount`로 판정. 진짜 재고 기반이 되며 [N-3] 멱등성 문제도 자연 해소된다.
- **조치 결과 (Resolved)**: `item_collected` 이벤트가 누적치(`amount`)가 아닌 현재 보유량 스냅샷(`current_total`)을 수신하고, 트래커는 대입(`current_amount = current_total`) 처리하도록 설계 및 계획서(Phase 6)를 전면 수정했습니다.

**[B-2] `objective_id`가 `instance_id`에 의존하나 draft는 instance 생성 전에 만들어짐 (순서 모순)**
- 위치: `2026-06-16-quest-agent-mvp-plan.md:132` (Phase 3)
- 내용: RuleGenerator가 `objective_id = {instance_id}:{item_id}`로 생성한다고 했으나, `instance_id`는 Phase 5 QuestManager의 영속화 시점에 발급된다. draft 시점엔 존재하지 않는다.
- 영향: Phase 3 구현 불가 또는 빈 instance_id로 잘못된 objective_id 생성.
- 제안: ① Manager가 instance_id를 draft 처리 전에 미리 발급해 RuleGenerator에 주입, 또는 ② objective_id를 instance 비의존 스킴(`{item_id}` 또는 UUID)으로 바꾸고 Manager가 instance_id와 묶어 저장. ②가 단순.
- **조치 결과 (Resolved)**: `objective_id`를 instance_id에 의존하지 않는 UUID 기반의 독립 식별자 스킴(`obj_{uuid}`)으로 변경했습니다. 계획서(Phase 3)와 Pydantic 모델(`QuestObjective.id`)에 모두 반영했습니다.

### 🟠 Major

**[M-1] feasibility 선행조건이 원재료(채굴/채집 자원)를 잘못 폐기**
- 위치: `2026-06-16-quest-agent-mvp-plan.md:142` (Phase 4)
- 내용: 선행조건이 "생산 레시피 해금 + 입력 재료 확보"인데, `resource_iron_ore` 등 원재료는 레시피가 없고 채굴/채집으로 얻는다(`resources.csv`의 `획득방법`).
- 영향: 원재료를 대상으로 한 `collect_item` 후보가 항상 `unreachable_prerequisite`로 폐기되어, 가장 흔한 초반 지원 퀘스트(광석 확보)가 절대 생성되지 않는다.
- 제안: feasibility = (해금 레시피로 생산 가능) OR (`획득방법`이 채굴/채집인 원재료) OR (이미 보유) 중 하나면 통과.
- **조치 결과 (Resolved)**: 원재료(레시피 없음) 또는 이미 보유 중인 재료의 경우에는 feasibility 선행조건 검사를 바로 통과하도록 검증 규칙을 세분화하여 계획서(Phase 4)에 반영했습니다.

### 🟡 Minor

**[N-1] 후속 단계 목록에 `collect_item`이 남아 있음**
- 위치: `2026-06-16-quest-agent-mvp-plan.md:178` (§6-1)
- 내용: "나머지 퀘스트 타입: `collect_item`/`setup_machine`/..."에 collect_item이 포함됨. 이미 MVP 타입이다.
- 영향: 범위 혼동.
- 제안: `produce_item`으로 교체.
- **조치 결과 (Resolved)**: 후속 단계 목록의 퀘스트 타입을 `produce_item`으로 정정하여 계획서를 수정했습니다.

**[N-2] `objective_id` 이름 충돌 (메인 vs 지원)**
- 위치: `2026-06-16-quest-agent-mvp-plan.md:126` (known_issues) vs `:132` (progress)
- 내용: `known_issues`의 `objective_id`는 메인 퀘스트 목표 id, progress의 `objective_id`는 지원 퀘스트 목표 id로 의미가 다른데 동명이다.
- 영향: 매핑·디버깅 시 혼동.
- 제안: `main_objective_id` / `objective_id`로 구분.
- **조치 결과 (Resolved)**: 메인 퀘스트의 목표 ID 필드명을 `main_objective_id`로 변경하였습니다. Pydantic 모델(`KnownIssue`, `MainQuestObjective`) 및 계획서의 데이터 스키마를 업데이트하여 네임스페이스 충돌을 해소했습니다.

**[N-3] `last_event_id` 단일값은 재정렬 재전송에 취약**
- 위치: `2026-06-16-quest-agent-mvp-plan.md:106`, `:155`
- 내용: 마지막 이벤트 id만 저장하면 `A→B→A` 순서 재전송 시 A가 중복 반영될 수 있다.
- 영향: 드물게 이중 카운트. (단 [B-1] 스냅샷 방식 채택 시 무의미해짐.)
- 제안: [B-1] 스냅샷 방식으로 함께 해소하거나, 처리 이벤트 로그/집합 도입.
- **조치 결과 (Resolved)**: [B-1]의 스냅샷 대입 방식을 채택하여 중복 누적으로 인한 이중 카운트 리스크가 원천적으로 해소되었습니다. 구식 이벤트 유입 방지를 위한 `last_event_id` 체크는 안전장치로 유지합니다.
