## 1. 변경 요약

지원 퀘스트(Support Quest) MVP Phase 1의 데이터 모델 계층이 추가되었다. 핵심 코드 변경은 다음 3개 파일이다 (나머지는 기획/리뷰 문서).

| 파일 | 변경 | 내용 |
|------|------|------|
| `backend/migrations/versions/0004_create_quest_tables.py` | 신규 | `quest_instances`, `quest_progress` 테이블 생성 Alembic 마이그레이션 |
| `backend/src/db/models.py` | 수정 | `QuestInstanceModel`, `QuestProgressModel` SQLAlchemy 모델 추가 |
| `backend/src/agents/quest_generator/models.py` | 신규 | 퀘스트 생성 에이전트용 Pydantic 스키마 (Context/Draft/Instance/Progress 등) |

마이그레이션 ↔ SQLAlchemy 모델의 컬럼 정의는 타입·nullable·server_default 기준으로 일치함을 확인했다.

## 2. 이슈 목록

### 🟠 Major

#### M1. 인덱스 부재 — 주요 조회 경로 전부 풀스캔 위험
- **위치**: `backend/migrations/versions/0004_create_quest_tables.py:27-89`, `backend/src/db/models.py:168-233`
- **내용**: 두 테이블 모두 PK 외 인덱스가 전혀 없다. 실제 조회 패턴상 인덱스가 필요한 컬럼:
  - `quest_instances.factory_id` — 공장별 활성 퀘스트 조회
  - `quest_instances.status` — 진행 중 퀘스트 필터링 (factory_id와 복합 인덱스 권장)
  - `quest_progress.quest_instance_id` — FK 조인 (PostgreSQL은 FK에 인덱스를 자동 생성하지 않음)
  - `quest_progress.last_event_id` — 멱등성 검사 시 조회 키
- **영향**: 데이터 누적 시 공장별 퀘스트/진행도 조회와 이벤트 멱등성 검사가 풀 테이블 스캔으로 떨어져 지연이 선형 증가한다.
- **제안**: 마이그레이션에 인덱스 추가.
  ```python
  op.create_index("ix_quest_instances_factory_id", "quest_instances", ["factory_id"])
  op.create_index(
       sa.Column(
      "ix_quest_instances_factory_status",
      "quest_instances",
      ["factory_id", "status"],
  )
  op.create_index(
      "ix_quest_progress_quest_instance_id",
      "quest_progress",
      ["quest_instance_id"],
  )
  ```
  SQLAlchemy 모델 컬럼에도 `index=True` 또는 `__table_args__`로 동일하게 선언해 autogenerate drift를 막는다.
- **조치 결과 (Resolved)**: Alembic 마이그레이션 파일(`0004_create_quest_tables.py`) 및 SQLAlchemy 모델(`models.py`)에 공장별 조회 컬럼(`factory_id`), 복합 필터 컬럼(`factory_id`, `status`), 그리고 FK 및 멱등성 조회 컬럼(`quest_instance_id`, `last_event_id`)에 대한 인덱스 구성을 완료했습니다.

#### M2. 멱등성/중복 진행 레코드를 막는 제약 부재
- **위치**: `backend/migrations/versions/0004_create_quest_tables.py:63-89`, `backend/src/agents/quest_generator/models.py:169-171`
- **내용**: `last_event_id`는 "멱등성 처리를 위한 마지막 처리 이벤트 ID"로 설명되지만, DB 차원에서 동일 `(quest_instance_id, objective_id)` 진행 레코드가 둘 이상 생기는 것을 막는 유니크 제약이 없다. 동시 이벤트 처리나 재시도 시 같은 목표에 대해 중복 progress 행이 생길 수 있다.
- **영향**: 멱등성이 애플리케이션 코드에만 의존하게 되어, 동시성/재시도 상황에서 진행도 이중 집계 또는 정합성 깨짐 위험.
- **제안**: `quest_progress`에 `UniqueConstraint("quest_instance_id", "objective_id")` 추가를 검토. 이벤트 단위 멱등성을 DB로 강제하려면 처리 이력 테이블 혹은 `(quest_instance_id, last_event_id)` 유니크도 후속 설계에서 고려.
- **조치 결과 (Resolved)**: 마이그레이션 및 ORM 모델의 `quest_progress` 테이블에 `(quest_instance_id, objective_id)` 유니크 제약 조건(`uq_quest_progress_instance_objective`)을 명시하여 데이터 무결성을 보장했습니다.

### 🟡 Minor

#### m1. FK에 `ON DELETE` 정책 미지정 — 고아 레코드 위험
- **위치**: `backend/migrations/versions/0004_create_quest_tables.py:84-87`, `backend/src/db/models.py:216-218`
- **내용**: `quest_progress.quest_instance_id` FK에 `ondelete` 동작이 없다. 인스턴스 삭제 시 진행 행이 남거나 제약 위반이 발생한다.
- **제안**: 도메인 정책에 맞춰 `ForeignKey(..., ondelete="CASCADE")`(인스턴스 삭제 시 진행도 동반 삭제) 또는 명시적 보존 정책을 결정해 선언.
- **조치 결과 (Resolved)**: `quest_progress` 외래키 정의에 `ondelete="CASCADE"` 옵션을 지정해 인스턴스 소멸 시 관련된 진행 정보가 고아로 유실되지 않고 동반 제거되도록 처리했습니다.

#### m2. Pydantic 검증 제약 불일치 — 수량 필드
- **위치**: `backend/src/agents/quest_generator/models.py:166-167` vs `:23-24`
- **내용**: `QuestObjective`는 `target_amount: gt=0`, `current_amount: ge=0`으로 제약하지만, 영속화 표현인 `QuestProgress`의 `target_amount`/`current_amount`에는 동일 제약이 없다. 같은 의미의 값에 검증 강도가 다르다.
- **제안**: `QuestProgress.target_amount=Field(gt=0)`, `current_amount=Field(ge=0)`로 통일. 경계값 검증의 시스템 일관성 확보.
- **조치 결과 (Resolved)**: Pydantic `QuestProgress` 모델 스키마에 수량 제약 검증 조건(`ge=0`, `gt=0`)을 반영하여 시스템 전체 모델 규격을 일관되게 정비했습니다.

#### m3. Pydantic ↔ DB 필드명 분기
- **위치**: `backend/src/agents/quest_generator/models.py:148-149` (`objectives`, `rewards`) vs `backend/src/db/models.py:192-193` (`objective_json`, `reward_json`)
- **내용**: 도메인 스키마는 `objectives`/`rewards`, DB 모델은 `objective_json`/`reward_json`으로 명명이 갈린다. 변환 계층에서 수동 매핑이 필요하며, 누락 시 조용한 직렬화 버그로 이어질 수 있다.
- **제안**: 의도된 분리라면 변환 함수(예: `to_orm`/`from_orm`)를 한 곳에 모으고 단위 테스트로 매핑을 고정. 이번 Phase에서 변환 로직과 테스트가 함께 들어오는지 확인 권장.
- **조치 결과 (Resolved)**: `QuestInstanceModel` 및 `QuestProgressModel` DB 모델 객체에 Pydantic 스키마 변환을 수행하는 명시적 `to_pydantic()` 매핑 메서드를 탑재하고, `test_quest_context_builder.py`에 이 헬퍼를 검증하는 단위 테스트를 추가해 직렬화 오작동을 차단했습니다.

### ⚪ Nit

#### n1. `created_at` 기본값 표현 불일치
- **위치**: `backend/migrations/versions/0004_create_quest_tables.py:56` (`sa.text("CURRENT_TIMESTAMP")`) vs `backend/src/db/models.py:200-203` (`func.now()`)
- **내용**: 동작은 사실상 동일하나 표현이 달라 향후 `alembic autogenerate` 시 불필요한 diff가 잡힐 수 있다.
- **제안**: 한쪽 표현으로 통일(예: 마이그레이션도 `sa.func.now()` 사용).
- **조치 결과 (Resolved)**: Alembic 마이그레이션 0004의 `created_at` 컬럼 server_default 값을 `sa.func.now()`로 일치시켜 autogenerate의 오차가 없도록 동기화했습니다. 또한, `0003_manual_rag_ingest`와 `0003_add_material_state`가 동일 부모(`0002_create_material_tables`)로부터 분기되어 다중 헤드가 발생한 문제를 해결하기 위해, `0003_manual_rag_ingest`의 down_revision을 `0003_add_material_state`로, `0004_create_quest_tables`의 down_revision을 `0003_manual_rag_ingest`로 순차 연결(선형화)하여 마이그레이션 멱등성 및 테스트 스모크 검증을 정상화했습니다.

## 4. 긍정적인 부분

- 모든 Pydantic 스키마에 `extra="forbid"`를 적용해 경계에서의 입력 검증을 엄격히 했다 (전역 코딩 규칙 준수).
- `default` ↔ `server_default` 쌍을 일관되게 선언해 ORM 생성과 DB 직접 삽입 양쪽에서 기본값이 보장된다.
- 마이그레이션 컬럼 정의와 SQLAlchemy 모델 정의가 타입·nullable·기본값 기준으로 정확히 일치한다.
- 한국어 docstring/Field description이 충실해 도메인 의도(예: `instance` 비의존 ID 스킴, `producible` 의미)가 명확하다.
- 타입 어노테이션이 전 구간에 적용되어 있고 `Literal`로 상태/유형 도메인을 좁혀 안전성을 높였다.
