## 2. 이슈 목록

### 🟠 Major

**M-1. 레벨 게이트로 인한 저레벨 데드락 가능성**
- 위치: `agents/quest_generator/rule_generator.py:50-53`
- 내용: `min_level(item) > factory_level`이면 해당 부족 자원을 **완전히 skip**한다. 그런데 레벨은 메인 퀘스트 완료로만 오른다(클라 소유). 메인 퀘스트가 고티어 아이템(예: tier-5)을 요구하는데 공장 레벨이 낮으면, 그 아이템에 대한 지원 퀘스트가 **영원히 생성되지 않는다**. 다른 부족 자원도 모두 게이트되면 `quest.none`만 반복.
- 영향: 가장 도움이 필요한 고티어 목표에서 지원 퀘스트가 침묵 → 플레이어 이탈 위험.
- 제안: (a) 게이트를 "메인 퀘스트가 직접 요구하는 아이템"에는 면제하거나, (b) 게이트 실패 시 한 단계 낮은 대체 목표(중간재)를 제시하는 폴백을 둔다. 최소한 게이트로 전부 막힌 경우를 로깅해 관측 가능하게.

**M-2. description 수치와 실제 target_amount 불일치 위험 (LLM 윤색 경로)**
- 위치: `agents/quest_generator/rule_generator.py:80-83`, `agents/quest_generator/compose_service.py:102-109`
- 내용: 강제 복원(force-restore) 대상은 `objectives/rewards/support_type/quest_type`뿐이고 **`description`은 LLM 윤색본을 그대로 사용**한다. 이제 `target_amount`가 `shortage_amount`·`main.required`와 분리(레벨 스케일)됐는데, 원본 description부터가 `"{shortage_amount}개가 더 필요... 우선 {target_amount}개를 모으세요"`로 **두 수치를 동시 노출**한다. 윤색 과정에서 LLM이 둘을 뒤섞거나 다른 숫자를 만들면 UI 목표(예: 10개)와 설명 문구가 어긋난다.
- 영향: 플레이어에게 보이는 목표 수량 혼동.
- 제안: description에서 수치 노출을 최소화(목표 수량 하나만)하거나, 윤색 후 description의 숫자도 검증/치환. 최소한 원본 description 문구를 단일 수치 기준으로 단순화.

### 🟡 Minor

**m-1. WS 내부 예외 메시지를 클라이언트에 그대로 노출**
- 위치: `websocket_gateway/quest_dispatch.py:122-130`
- 내용: `build_error_payload("INTERNAL_ERROR", f"An internal error occurred: {str(exc)}")` — 예외 문자열을 응답에 포함. 내부 구현/스택 정보가 클라로 누출될 수 있다.
- 제안: 전체 예외는 `logger.exception`으로만 남기고(이미 있음), 클라 응답은 고정 일반 메시지로.

**m-2. 멱등성 미구현 (request_id 재사용 시 중복 생성 가능)**
- 위치: `websocket_gateway/quest_dispatch.py` 전반
- 내용: `request_id`를 응답에 echo만 하고 처리 기록은 없다. 동일 `request_id` 재전송 시 compose가 다시 실행됨(서버 가드 상한 3·동일아이템 차단으로 폭주는 막히나 완전 멱등은 아님). 계획서에서 "1차 허용"으로 합의된 사항이나 코드/문서에 한계 명시 필요.
- 제안: 후속 과제로 `request_id` 처리 기록 도입. 현재는 주석으로 한계 명시.

**m-3. 모듈 임포트 부작용 결합**
- 위치: `websocket_gateway/quest_dispatch.py:17` → `from agents.quest_generator.quest_router import get_phrase_refiner`
- 내용: `quest_router`는 임포트 시점에 `_default_adapter = create_llm_adapter(...)`를 **모듈 로드 시 생성**한다. WS 디스패처가 라우터를 임포트하면서 이 부작용에 묶인다(불필요한 역방향 의존: gateway→router).
- 제안: `get_phrase_refiner`(또는 기본 refiner 제공)를 `compose_service` 또는 공용 deps 모듈로 이동해 router 의존 제거.

## 4. 긍정적인 부분

- **깔끔한 추출:** compose 파이프라인을 `ComposeResult`로 채널 중립화하고, 라우터는 reason→HTTP 매핑만 담당 → REST 외부 계약 완전 보존(기존 `test_quest_router` 회귀 통과).
- **견고한 WS 입력 검증:** payload dict / context dict / factory_id non-empty string을 단계별로 확인하고 각기 명확한 `INVALID_PAYLOAD` 반환.
- **동시성 처리 적절:** `asyncio.to_thread` 안에서 `get_db_session`을 열어 세션을 워커 스레드 내부에 한정(이벤트 루프 비차단, 세션 공유 회피).
- **계획 대비 충실:** 레벨 스케일 + `producible` 상한 + 레벨 게이트가 계획서 Phase 3 결정(생산 불가 시 과대 수량 방지 포함)을 정확히 반영.
- **테스트 커버리지:** composed/none/malformed/unknown-type + echo 필드 + 레벨 케이스까지 23개 통과.
- **게이트 데이터 분리:** `_ITEM_MIN_LEVELS`를 game_data에 테이블로 둬 밸런싱 데이터를 코드 로직과 분리.
